31. **Service options stay at their defaults in `Build`** (session lifetime, throttle, argon2id parameters): page 1's schema has no `auth` section. Add one when a value needs tuning.
32. **Close codes and bad messages:** the layer closes with 4001 (slow consumer), 4002 (no pong), 4003 (kicked by the handler, the reason says why), 4004 (unknown or malformed message); oversized frames get the standard 1009 from the library. An unknown or malformed message closes the connection rather than being ignored, since a well-behaved client never sends one. OnClose gets nil for a peer's normal closure, the `CloseError` when the server decided, else the read error.
33. **Decoding tolerates unknown fields inside `d`** (not in the envelope), so an older server accepts a newer client's extra fields; the golden tests still pin the exact output. Message names are the Go type names; every struct is registered in `internal/protocol`, and page 4's catalogue is checked by a test.
34. **Wire shapes the design left open:** `Damage.source` and `target` are `p:<character id>` or `m:<mob id>`; `Delta` carries changed entities in `players`, `mobs`, `drops` and departures in `removed_*`; `Welcome` carries `tick` and `server_time` (Unix ms); `PartyState.party` is null when there is none; `Response` has `ok`, `code`, `message`. The golden files are the reference for the client.
35. **Inputs are held keys, applied by sequence:** all inputs that arrive in one tick are sorted by `seq`, the newest becomes the held keys for that tick's three sub-steps, and `ack_seq` is the newest applied. Flooding inputs therefore never speeds a character up (B2), and the client predicts with the same one-input-per-tick rule.
36. **No separate Correction from the world:** every Delta carries the player's own authoritative state when it changed; the client compares that with its prediction at `ack_seq` and reconciles. The gateway can still emit page 4's Correction from the same data if the client wants a dedicated message.
37. **A Delta goes to every player every tick,** even when empty, so `ack_seq` stays fresh; a sink that refuses an event (full queue) gets its player removed on that tick and reported to the others on the next. Instances share nothing: each has its own inbox, players and tick; the only shared thing is the persistence queue.
38. **Checkpoints are tick-counted** (interval ÷ tick interval ticks) rather than clock-based, so they are deterministic under `synctest`; `Instance.Run` checkpoints everyone on the way out and `World.Run` flushes the queue after the instances stop.
39. **Registry as a mutex-guarded map, not an actor goroutine** (page 3 lists it as one actor): the registry's critical sections are two map writes, so a mutex gives the same guarantees with less machinery. Identity is set once by Hello and read from the session afterwards; a message naming another character still acts as the sender.
40. **Hello failure paths:** outdated protocol, bad token, someone else's or an unknown character, and a malformed ID all answer with Kicked (the reason) then close 4003; a join failure or a character on an unknown map close 1011 without a reason, since those are server faults. A message before Hello, or a second Hello, closes 4003 without a Kicked message.
41. **Rate limits are per connection and per message type** with page 4's numbers; an over-limit Input is dropped silently, an over-limit command with a request ID gets `Response{rate_limited}`. Commands from later steps (Attack, PickUp, chat, party, inventory) answer `unavailable` when they carry a request ID and are ignored otherwise, so the client can be built ahead of the server.
42. **Kicked before the close frame:** wsconn now flushes the send queue after the writer stops and before the close handshake, so a Kicked queued right before `Close` reaches the peer. Slow-consumer and missed-pong closes still drop the socket at once.
43. **The world and the persistence worker run as server tasks** started by `Run` beside the listener and stopped after the listener drains; the end-to-end stack starts the same tasks itself since it serves the handler through httptest.
44. **Combat draws randomness in a fixed order** (hit, variation, crit; a miss draws once) from the instance's generator, a PCG seeded by `Options.Seed`, recorded and readable through `Instance.Seed()`; tests inject a fixed roll. The Bowman's shot leaves at chest height (half the character box) and the first mob crossed within 420 px is hit; the Warrior's box stands on the feet line in front.
45. **Mobs patrol the ground they spawn on:** the solid or platform directly under the spawn point gives the bounds, trimmed by half the mob's width; with no room they stand still. They spawn all at once on the first tick, then one per expired respawn timer, never above the area's maximum. A cooldown or an invulnerability window is counted in ticks (rounded up).
46. **Contact damage knocks the player 16 px away with a small hop** (page 5 says "knocked back" without numbers) and starts the one-second invulnerability whether the hit landed or not; one mob per tick can touch a player.
47. **Respawn away from the town is a transfer:** the player gets Respawned and Teleport (MapChange) directly, the map's others get Respawned and a removal, the checkpoint names the town, and the World joins the player to the town's instance from a goroutine so the tick never waits. The gateway re-points the session on Teleport. The same path serves portals in step 14.
48. **Level-ups are saved as jobs** on the same persistence queue as checkpoints (`world.Job` with one field set); the worker calls `SaveLevelUp` right away, so a crash after a level-up keeps it.
49. **End-to-end fight rows place characters in the forest by updating their row in the database** (no portal until step 14), the way a checkpoint would have left them; each row runs on its own stack because the login throttle is per IP.
50. **Idempotency keys serialise through a transaction-scoped advisory lock** on the (owner, scope, key) hash, so two concurrent uses of one key run the command once and both get its response, instead of the second failing on the primary key at commit. The owner is the account, as page 2 says; the service takes an `Actor` with both the account and the character.
51. **Inventory rules in Stage 1:** an add fills the first stack with room, then opens the first free slot of the item's tab, else `inventory_full` with nothing written; a move onto a matching stack merges what fits and leaves the rest (the emptied source is destroyed); a move onto a different item is `conflict`; an item never changes tab; a `moved` event with delta 0 records slot changes, so check 5 holds through moves. Outbox events: `ItemLooted` (drop cause), `ItemGranted` (starter), `ItemDiscarded`.
52. **Starter items live in `classes.yaml`** (`starter_items`, validated against the items after they load): Warrior a wooden sword and 5 red potions, Bowman a short bow and 5 red potions. Character creation calls `uow.Starter().GrantStarter` inside its transaction; `internal/server` binds it to `items.Within(itemStore.UnitOfWork(tx))`, and a nil factory (tests, the migrate binary) grants nothing.
53. **Check 6 ("total per template equals created minus discarded")** is implemented as: per template, the quantity held across all rows (destroyed ones hold 0) equals the sum of every event's delta for that template's items, which is the same statement once every change is an event.

54. **A drop is in memory only, with a wire ID and a UUID minted when it lands;** that UUID is the idempotency key of its pickup (page 2's "drop ID"), so a double pickup, a retried job and a replay after a crash all resolve to one item. Drops land at the mob's x ± 24 px, 20 px apart when a mob drops several, on the mob's ground line; the 40 px pickup range is measured from the centre of the character's box.
55. **A pickup reserves the drop inside the tick and hands one job to the worker pool;** the result returns through the instance's inbox, so the tick never waits. Success removes the drop for everyone and sends InventoryChanged to the picker; any failure releases the reservation and sends the picker a Response with ok false and the error code (there is no request ID on PickUp). A worker retries once on a non-rule error (the key makes it harmless); a full queue (1024 jobs) releases the reservation and answers "try again in a moment".
56. **InventoryMove and InventoryDiscard run on the connection's goroutine with a 5 s timeout,** never on a tick; the reply is a Response for the request ID plus InventoryChanged with the changed slots. Welcome carries the inventory from the item service. With no item module wired (tests), both commands and pickups answer unavailable.
57. **The crash test runs `cmd/gameserver` as a separate process from the test binary** (built into a temp dir, configured through CONFIG_PATH and FINGA_* variables over the Testcontainers database), kills it with Process.Kill (TerminateProcess on Windows, SIGKILL elsewhere), checks the invariants, starts it again, checks again and compares each hunter's Welcome inventory with the database. It is skipped under `-short`.
58. **The end-to-end "retried pickup" row calls the item service directly over the stack's database with the worker's exact input, twice;** forcing a worker retry through the wire would need a fault injected into production code. The world test covers the worker's retry path with a fake.
59. **Economy jobs in flight are a gauge** (`economy_jobs_inflight`) fed by the pool through an observer, next to page 3's other metrics.
60. **The linked town is a `town` map property in Tiled, required on hunting maps;** a town names itself, and the loader refuses a value that is not a loaded town. The respawn uses it instead of "the one town". A map whose town is not loaded (test-only maps) respawns in place.
61. **EnterPortal fires when the character's feet are inside a portal rectangle, bottom edge included** (an arriving character stands exactly on it, so one more EnterPortal takes them straight back). The handoff order is one function shared with the respawn: Teleport to the player, a checkpoint that already names the target map and arrival point, detach from this instance, then the World joins them to the target from its own goroutine. A second EnterPortal in the same tick finds the player gone and is ignored; off a portal, dead, or without a mover nothing happens and nothing is sent (EnterPortal has no request ID).
62. **Town maps run no combat at all:** attacks are cleared without resolving and contact damage is skipped, so even a mob placed in a town by a test is harmless; the data loader already refuses spawns in towns. The "no penalty in a town" branch stays for the day something else can kill there.

With the whole floor, every mob drifted across the map over time: the forest's slimes left their field and a mushroom was killed at x 464. Page 3 now says so. Notifications go out under the lock through the gateway's non-blocking sends.

Page 4 says so. Cleaning strips control characters only; the client renders plain text.

98. **`gen-gamedata.ts` runs as plain TypeScript under Node 24's type stripping,** with the `yaml` package as the only dependency, and emits one `as const` module per data file; equipment gets `max_stack` 1 and everything else 100 unless the YAML says otherwise, and class cooldowns become `cooldown_ms` integers, so the client never parses a duration string. `src/gamedata/` is git-ignored and regenerated before every script that compiles code.
99. **`parseMap` mirrors the loader's checks that the client can make on its own** (the map shape, the six layers, `kind`, `town`, portal and spawn properties, exactly one player spawn) and leaves cross-map checks (a portal's target exists) to the server, which has already validated every map it serves.
100. **The socket's close decisions live in one function** keyed on the server's close code and the Kicked reason that preceded it: 4001, 4002, a plain drop and `server_restart` reconnect with full-jitter backoff; `unauthenticated` and `session_expired` clear the token and end as `session_ended`; `logged_in_elsewhere` and `abuse` end as `kicked` with the reason; `outdated_protocol` ends with its own reason so the app can reload the page (the socket itself never touches `location`); 4004 ends as `bad_message`. A `reconnecting` flag makes a second reconnect a no-op while one is scheduled.
101. **A request is re-sent at most once across a reconnect,** with a new `req` and the same payload (so the same idempotency key); a second drop rejects it as `disconnected`, and the Response for the old `req`, should it arrive, is handed to `onUnmatchedResponse` like any Response without a known `req`. Request timers count from the first send.
102. **The client drops a silent connection itself:** a Ping every 15 s with a 5 s Pong deadline closes the socket with a normal code and lets the close path reconnect, so the server's 4002 after 30 s is not the only way out of a dead connection. The Pong also gives a round-trip estimate and a server-time offset for later steps.
103. **`sendInput` refuses a second Input for the same tick number** and owns the sequence counter; actions reuse the current number. The caller (C08) passes its tick counter; the socket never looks at a clock for this.
104. **The REST client reads the token from the holder on every call** and never caches it, so the rotation the socket applies on Welcome reaches the next REST call without any wiring; `logout` clears the holder even when the server call fails.
105. **The hand-run smoke script is standalone** (Node's fetch and WebSocket, raw JSON) rather than importing `net`, because the `@/` alias and the generated gamedata belong to the bundler; it checks the wire, not the client code, which the unit tests cover.
106. **Every store is built by one helper, `defineStore`,** that returns the vanilla store for Phaser code (`getState`, `subscribe`), a `use` hook with a selector for React, and `reset` for tests; state changes only through the actions defined in the store, which take protocol payloads where there is one (`applyWelcome`, `applyInventoryChanged`, `applyPartyState`, ...).
107. **The inventory store never rules:** it places exactly what Welcome and InventoryChanged say, slot by slot, so a refused move (a Response with nothing else) changes nothing, and "a slot never holds two items" is a property of the payload format the store preserves. A slot the tabs do not have is ignored rather than thrown, as the server would never send one.
108. **Components never import a store** (page 7: folders in the same layer do not import each other), so the Window reports focus changes through an `onFocusChange` prop and the feature that opens it sets `ui.captureKeyboard`; the C05 page's wording ("Window sets ui.captureKeyboard while focused") is read that way. Components also take `onClose` rather than closing themselves.
109. **Key presets are `KeyboardEvent.code` values, not characters,** so the layout works the same on any keyboard language; `up` is one action that both climbs and, while standing on a portal, enters it (C12 decides which from the sim state), and `NumpadEnter` opens chat like `Enter`.
110. **The connection store has its own status union** (`disconnected`, `connecting`, `connected`, `reconnecting`, `kicked`) rather than importing the socket's, since state and net are siblings; `app/wiring` (C06) translates one into the other.
111. **The settings cache is read once at store creation** and written on every change, through a storage parameter that tests can replace; any storage failure falls back to Classic silently, because the account's setting arrives from the server right after login anyway.
112. **Local validation mirrors the server's rules only to save a round trip:** a bad username, password or character name is refused before the request leaves, with the rule shown, but whenever the server answers with an error its `message` is shown verbatim (a 401, the name conflict, the cap conflict, the login throttle), so the client never invents a text the server did not send.
113. **The three-character cap is applied locally only as a convenience:** once the list already holds three, the create form is disabled with a notice; the cap itself stays the server's, and its conflict message is shown when the list was stale.
114. **Which socket closes end the session is decided in `app/wiring`:** `kicked`, `session_ended`, `outdated_protocol` and `bad_message` set the connection to `kicked` with the reason and call `leaveWorld` (character, inventory, party and chat cleared, session logged out), so the login screen shows why; a `user` or `no_token` close only marks the connection disconnected. An outdated protocol also reloads the page, since only a newer bundle can help.
115. **Per-session screen state lives in a `LoggedIn` component mounted only while the session is logged in,** so a log out or a kick resets the chosen character and open windows by unmounting rather than by an effect setting state, which the React hooks lint refuses.
116. **Text fields capture the keyboard through `features/shared/use-keyboard-capture`,** which sets `ui.captureKeyboard` on focus and clears it on blur (the feature side of decision 108); the forms before the world use it too, so C08's key handling needs no special case for the screens.
117. **The settings panel writes the cache first and the server second:** the next frame already uses the chosen preset, a failed `PUT` shows the server's message but keeps the local choice, and the account's saved preset replaces the cache when the panel opens, so the account wins across devices.
118. **The hand check ran as temporary test files, not in a browser:** the Chrome extension was not connected, so the App was driven in jsdom against `make up` and the `GameSocket` in a Node environment; the two could not be combined because Node's WebSocket rejects jsdom's `Event` objects. Both files were deleted after the run. A browser hand check stays owed at the M1 milestone end, when the author plays.
119. **Platformer Pack Remastered stands in for Platformer Pack Redux,** which kenney.nl no longer hosts (only an OpenGameArt mirror remains): the same vector family, 128 px tiles, enemies and items and 128x256 players, all drawn at scale 0.25 so one tile is one 32 px grid cell and a player is 32x64 over the 24x56 hitbox. The players come from the same pack (alien Blue for Warrior, Green for Bowman) rather than from "Platformer Characters", whose 80x110 poses reach 32 px only by a non-exact scale. Mobs: slimeGreen, snail (orange_mushroom), mouse (wild_boar), fly (cave_bat); tints come with C10.
120. **"Generic Items" is household and office art,** so only its flask is used (tinted red and blue for the potions); the other ten item templates are original 32 px shapes drawn at runtime by the Preloader in the Kenney palette and listed in `LICENSES.md` as original, per the finga rule for templates without a match. The downloaded zips stayed in a scratch folder; only the 47 PNGs in use are in the repo.
121. **The app drives Phaser through a `GameHandle`, not React state:** the handle exists before the canvas (so `App` can hold it in `services`), `PhaserGame` attaches it to `#game` once and detaches on unmount (which is also the React double-mount guard), and `LoggedIn` calls `enter` when the Welcome resolves and `leave` on the way out or on unmount, so a kick leaves the world without an effect setting state. An `enter` before the canvas exists is kept and started on attach.
122. **The World scene waits for the Preloader when it must:** the Preloader sets an assets-ready flag in the registry and emits a game event; a World started before the flag builds on the event, so entering the world a moment after the page loads never draws with missing textures.
123. **The map is drawn from the object layers with tile sprites,** as plain data from `world-layout` (a solid is a surface row plus fill, a thin platform a half tile from its top edge, a rope a ladder one tile wide, a portal a door top and middle), and the look is per map (dirt in town, grass in the forest, stone in the cave; an unknown map gets the forest look). The player sprite stands hidden at the map's entry until the first Snapshot or Delta names it, since Welcome carries no position; until C08 it follows the server's state directly.
124. **The input queue is cut once per tick after the inbox drain, not per insert:** a burst of six inputs arriving in one tick leaves the newest two queued (as step 18's test says), whereas cutting on each insert kept the fifth as well. The queue still never outgrows one tick's drain limit, so a flooding client cannot grow server memory.
125. **`ack_seq` stays the sequence number of the input applied this tick;** on a tick with no queued input the last held keys are re-applied and `ack_seq` repeats, which the client's reconciliation reads as a match for the same tick and ignores (its entry was already dropped).
126. **Reconciliation compares a whole tick:** the Delta for `ack_seq` describes the server after that tick's three sub-steps, while the client may be one or two sub-steps into it when the Delta lands (localhost round trips are shorter than a tick), so the predictor finishes the tick on a copy before comparing. A reset replays each later entry for only the sub-steps it has run, so the frame loop carries on from the right point. The client-only fields (`ground`, `drop_platform`, `drop_timer`) are not on the wire: a reset derives the platform stood on from the position and assumes no drop-through in progress.
127. **A late Input breaks the exact match under step 18 as written:** a server tick with an empty queue re-applies the held keys, which the client never predicted, so the next ack is one tick off and the client resets (10 px). Measured live: 1 reset per 100 ticks on a drift-free sender, 12 with a sender that drifts a few ms per tick. Options sent to the finga session: hold the player on an empty queue (recommended; makes the match exact whatever the timing), one tick of client slack, or accept the occasional reset. Ruling (finga, the same day): hold the player on an empty queue, with a cap of 5 ticks after which the last keys are simulated again so a stalled client cannot hang in the air; a stall past the cap is the design's one real disagreement (a single reset). Built as the second step 18 commit; the opt-in live test expects 0 resets per 100 ticks under jitter and exactly 1 after an 8-tick stall, which it measured at 0 and 100 ms one-way delay.
128. **Keyboard capture is read two ways on purpose:** the key binding asks the `ui` store on every key down (so a key pressed while typing never reaches the game), and the input sender is told on every change through a store subscription (so the all-released Input goes out the moment a text field takes focus, not at the next tick). Key ups are honoured while captured so no key sticks when the player tabs into chat with a key down.
129. **The World scene sends nothing before the first Snapshot:** the frame loop waits until the server has named the local player, so the sequence numbers start with a known position and no Input is wasted on a player the server has not placed. A later Snapshot (a reconnect) resets the predictor the same way.
130. **Remote players are drawn on the server's tick clock, not on arrival time:** every Snapshot and Delta state is stamped `tick * 50 ms`, and the render clock sits 100 ms behind the newest tick, advancing with local time between messages, so network jitter moves nothing and a late message only shortens the lead. Past the newest state a player is extrapolated along its velocity for at most one tick, then stands.
131. **A removed player is drawn until the render clock passes the removal tick,** so someone who leaves is not cut off two states early; a Snapshot (a reconnect) replaces the whole set at once, since it is the map's truth. Remote state never touches a store (page 7): the scene keeps the buffers and the views.
132. **A Welcome after a reconnect on the same map hides the local player and clears the others until the next Snapshot,** which places everyone again; a different `map_id` restarts the scene for the new map with the same character. The kick cases stay with `app/wiring` (decision 114); `server_restart` never reaches the scene because the socket reconnects on it (C04).
133. **The HUD's EXP maximum is the generated curve's value for the level** (the `character` store's `expToNext`, decision 105), and at the cap the bar is full and says MAX; the HUD reads only the store, so the per-tick world data never re-renders React.
134. **Both edges of invulnerability are forced into a Delta by the `changed` flag:** the start in `contactDamage` (the knockback moves the player anyway, but the flag does not depend on that) and the end in `simulate` on the tick `invulnUntil` equals, which runs for every map and every living player, so a player who stands still after a hit still gets the cleared flag exactly one second later. The view reads `invulnUntil > tick`, so the end-edge Delta already shows it false.
135. **The death penalty's `ExpGained` is private and only when it took something:** `kill` compares the EXP before and after `DeathPenalty` and appends the message to the player's private events (sent after the tick's Delta, with Died); in a town, or at the start of a level, nothing is sent, as the step says. The golden Delta now carries two players so the client's codec test covers the omitted-when-false rule on the same file.
136. **Combat on the client is a view:** mobs are tracked and interpolated exactly like remote players (positions on the server's tick clock, no velocity on the wire so no extrapolation), a Damage drops a mob's bar or the local player's HP at once and the next Delta confirms or corrects it, and the only rule copied from the server is the attack cooldown, read from `gamedata` and used solely to gate sending (page 9, Rules). Numbers, the swing pose and the arrow streak are cosmetic and need nothing the server does not send.
137. **Death, respawn and map change are one reducer (`map-transition`)** over Died, Respawned and MapChange for the local player, returning actions the scene applies: die (nothing sent or predicted, the character lies down, the overlay shows), respawn-here (prediction reset to the server's position, HP from the message) and change-map (the scene restarts for the new map and waits for its Snapshot). C12's portals reuse the change-map path. Other players' deaths need no handling: their Deltas carry `dead`.
138. **The death penalty shows through the same ExpGained the HUD already handles:** the store keeps the last change's amount with a counter, and the HUD shows a gain or a loss for two seconds per change; the invulnerability flash follows the server's `invulnerable` flag in the player's own Snapshot and Delta state, never a local timer (backend step 19).
139. **The inventory never moves an item before the server says so:** a drag marks the item pending in its own slot and sends InventoryMove with one idempotency key kept for that drag; an ok Response only clears the mark, InventoryChanged does the moving, a refusal clears the mark and shows the server's words, and a timeout or a lost connection offers Retry with the same key (net re-sends by itself across a reconnect, C04). Cross-tab drags are refused in the window, matching the server's rule, so no request is wasted on them.
140. **A refused pickup is a toast, not a window:** PickUp carries no request ID, so its refusal comes back as a Response with none, which `app/wiring` turns into a short notice through the `toasts` store (`inventory_full`, `unavailable`, or the server's message); an out-of-range pickup gets no answer at all, which is what the range hint on the nearest drop is for. One PickUp per tick, through the input sender's tick number.
141. **Item icons in the window are the template's initials coloured by tab,** since the Phaser textures are not available to React and the Kenney packs have no RPG item art (decision 120); the names come from the generated item templates. A proper icon set can replace the tile without touching the window's logic.
142. **A map change is a scene restart, not a swap in place:** the change-map action from `map-transition` (C10) fades the camera out and restarts the World scene with the new map id and the arrival position, so the collision view, the interpolation buffers, the mob, drop and player views and the predictor are all rebuilt from nothing and no stale entity can survive a hop; the following Snapshot places everyone. The restart also resets the portal system, so a key still held on arrival cannot bounce the player back until it is released and pressed again.
143. **The up key is both climb and portal:** the keyboard binding keeps one movement action, and the scene's key target forwards it to the input sender and, on a fresh press with the feet inside a portal rectangle (edges included, the server's `standsIn`), to the portal system, which sends EnterPortal once. The sim decides the climb; the server decides the hop.
144. **The party window never changes membership itself:** every command (invite, respond, leave, kick, promote) is a request with a request ID whose refusal shows the server's words, and the members list, the leader and the invite list come only from PartyState and PartyInvited; the invite countdown is cosmetic, since the server expires invites too, and an invite that expired before the answer is simply dismissed.
145. **Who can be invited comes from a small `nearby` store,** fed by the World scene only when a remote player arrives or leaves (never per tick, page 7), since PartyInvite takes a character id and React needs the names; members of the current party are left out of the list.
146. **Chat has no window:** a box on the HUD whose input the Enter key focuses through the `ui` store (the World scene sets `chatOpen`, the box focuses on it), captures the keyboard while focused and releases it on Enter or Escape, so the input sender sends an all-released Input the moment the player starts typing (decision 128); a `/p` prefix is the party channel; refusals arrive as Responses with no request ID and show as toasts (decision 140).
147. **Every failure has its own code, and the handler owns the mapping** (asked for by the user on 2026-10-23): services return plain sentinel errors named for the failure and wrap causes with `%w`; `internal/handler/errmap` turns each into a status (the class of failure), a stable code of its own and the player message. The generic codes and `pkg/errs` are gone. HTTP and the WebSocket share the one table.
148. **The player messages moved into the table unchanged,** so nothing a player reads differs; the only new text is for the login race (`session_race`, "another login is in progress, try again"), which before reused "another session is active".
149. **Errors that never reach a client are listed as internal-only** (`world.ErrBusy`, `ErrNoMap`, `ErrStopped`: the gateway closes the connection and logs them), so the guard test still accounts for every exported error in one file.
150. **An error the table does not know is logged with its cause:** the request log carries the code of every refusal and, for `internal`, the error at level ERROR; the gateway logs `command failed` with the command, and the sink logs `pickup failed`. Before, a database failure behind a 500 or a failed command was never logged.
151. **The handler's own failures got specific codes too** (`malformed_body`, `missing_field`, `body_too_large`, `no_such_endpoint`, `method_not_allowed`, `rate_limited`, `chat_unavailable`, `parties_unavailable`, `inventory_unavailable`, `not_implemented`), and a test keeps every code unique and snake_case.
152. **`testdata/errors/codes.json` is the contract for codes,** written from the table with `go test ./internal/handler/errmap -update`; the client's `errorCodes` must equal it, so a new server code fails the client's tests until the client knows it.
153. **The Go module moved whole into `server/`, with the content and contracts it owns** (`data/`, `api/`, `testdata/`, `configs/`, `migrations/`; asked for by the user on 2026-10-23). Every relative path in the Go tests stays as it was, the Docker build context is `server/` alone, and the client's reads from `../server/` say plainly that the server is the reference. Keeping the shared files at the root was the alternative; it was not taken because the server writes the golden files and owns the content the client generates from.
154. **`infra/` holds how the game runs:** `docker-compose.yml` now, building `../server`; the High-level design already planned `infra/` for Terraform, and the nginx configuration and Grafana dashboards join it in Stage 2. The Dockerfile stays with the code it builds, in `server/`.
155. **Nothing else moved:** the Go module keeps the path `finga`, so no import changed; the root Makefile stays the one entry point with the same targets; `docs/`, `tools/` and `.github/` stay at the root.
156. **Local overrides moved with the server:** `server/.env` (Compose passes the same file to the container) and `server/configs/config.local.yaml`, since the binaries run from `server/`.
157. **The binaries read the YAML file and their environment, nothing else** (asked for by the user on 2026-10-23). Loading `.env` is the job of whoever starts the process: Compose's `env_file` for `make up`, `make run` without Docker, the test harness for the crash test. The precedence `.env` < real environment no longer exists in code; in `make run` the file's values win over the shell's, and in Compose the `environment` entries win over `env_file`.
158. **`make run` is the documented way to start the binaries without Docker:** it sources `server/.env` with `set -a`, so values with spaces or `&` are quoted, which Compose's `env_file` also accepts.
159. **Two `.env` files with two readers:** `infra/.env` holds what Compose itself interpolates (the host ports); `server/.env` holds the game server's settings and goes into the container whole. One file for both would mean `--env-file ../server/.env` on every Compose call, and Compose refuses to start when that file is missing, which it is in a clean clone.
160. **Readiness is local** (asked for by the user on 2026-10-23): `/readyz` is 200 while this process listens and is not shutting down, and checks no dependency. Postgres is shared by every instance, so failing readiness on it would take them all out of rotation at once; a database outage is seen in the logs, request errors and `db_tx_duration_seconds`.
161. **Startup still needs the database:** `Build` fails when the pool's first ping fails, so a server that becomes ready has reached Postgres at least once. Readiness turning 503 at the start of shutdown is kept and now tested, so new traffic stops while in-flight requests drain.
