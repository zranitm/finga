# 4. Protocol

## REST

JSON bodies. Authenticated calls send the header `Authorization: Bearer TOKEN`. Errors return an HTTP status and a body with `code` and `message`; the code names the exact failure (see Error codes below).

| Method and path | Purpose | Notes |
| --- | --- | --- |
| `POST /api/accounts` | Sign up | Username 3–16 characters (letters, digits, underscore); password at least 8 characters |
| `POST /api/sessions` | Log in | Returns an opaque token and revokes any older session. Rate-limited per username and per IP. |
| `DELETE /api/sessions/current` | Log out |  |
| `DELETE /api/sessions` | Log out everywhere | Ends every session of the account and closes its game connections |
| `GET /api/characters` | List my characters |  |
| `POST /api/characters` | Create a character | Name and class. Name 3–12 characters (letters and digits, starting with a letter), unique ignoring case; class one of the stage's playable classes |
| `GET` and `PUT /api/settings` | Read and save settings | Control preset (B6) |

## WebSocket

- Connect to `/ws`. The first message must be Hello within 5 seconds, carrying the token, protocol version, and character ID. Otherwise the server closes the connection. Close codes the server uses: 4001 slow consumer (send queue full), 4002 no pong, 4003 kicked (the reason is in the preceding Kicked message, or in the close reason for a missing Hello or a message before Hello), 4004 unknown or malformed message; oversized frames get the standard 1009.
- Each frame is one message in an envelope: a type and data, plus an optional input sequence number, request ID, and server tick.
- The encoding sits behind the codec interface in `pkg/wsconn`. The message catalogue below is the same whatever the encoding.
- Commands that expect a result carry a request ID, and the server answers with a Response carrying the same ID.
- Commands that change items or coins also carry an idempotency key, generated by the client once per player action and reused on retry.

Example envelopes:

```json
{"t": "MarketBuy", "req": "r-42", "d": {"listing_id": "…", "idempotency_key": "…"}}
{"t": "Response", "req": "r-42", "d": {"ok": true}}
{"t": "Delta", "tick": 81234, "d": {"ack_seq": 117, "players": [], "mobs": []}}
```

## Wire shapes (Stage 1)

The reference for every message is `api/asyncapi.yaml` and the golden files in `testdata/contracts/<Type>.json`, which the server's and the client's tests both check. Shapes this page leaves open:

- **Damage** `source` and `target` are `p:<character id>` or `m:<mob id>`.
- **Delta** carries changed or new entities in `players`, `mobs`, `drops`, and departures in `removed_players`, `removed_mobs`, `removed_drops`; `ack_seq` is the latest input sequence applied for the recipient.
- **Snapshot** and **Delta** players carry `dead` and, since backend step 19, `invulnerable` while the second of invulnerability after contact damage lasts; both are omitted when false.
- **Welcome** carries `character`, `inventory`, optional `party`, `map_id`, `tick`, and `server_time` (Unix milliseconds), and since step 16 `token`: the rotated session token the client uses from then on (see Trust model).
- **PartyState** has `party: null` when the player has none.
- **Response** has `ok`, and `code` and `message` when `ok` is false. Commands from a step not built yet answer `not_implemented`; a command whose module is not wired answers `chat_unavailable`, `parties_unavailable` or `inventory_unavailable`. A failed pickup and a refused chat line come back as a Response with no `req`, since PickUp and ChatSend carry none.

## Error codes

Every failure has its own code, so a client and a log line both say exactly what went wrong: `name_taken`, `party_full`, `not_party_leader`, `inventory_full`, `chat_rate_limited`, never a bare `conflict`.

- **Services** return plain sentinel errors named for the failure (`party.ErrFull`, `character.ErrNameTaken`) and wrap a cause with `%w`. They carry no code and no player text.
- **The handlers** own the mapping, in `internal/handler/errmap`, shared by REST and the WebSocket: each error gets an HTTP status for its class (400 bad input, 401, 404, 409 a rule the request ran into, 429, 503, 500), its own code, and the message a player sees. The handlers' own failures have codes there too: `malformed_body`, `missing_field`, `body_too_large`, `no_such_endpoint`, `method_not_allowed`, `rate_limited`, `not_implemented`, and the three `*_unavailable` codes above.
- **An error the table does not know** answers `internal` with "something went wrong" and is logged with its cause at level ERROR. A test fails when a module declares an exported `Err` variable with no row.
- **The list** of every code with its status and message is `testdata/errors/codes.json`, written from the table; the client's code list is tested against it.
- **Stage 2** adds its own, such as `insufficient_balance` and `listing_unavailable`.

## Rate limits

Token buckets per account in the gateway (`pkg/ratelimit`), enforced on the connection, which equals the account while one active session per account holds. An over-limit Input is dropped; an over-limit command with a request ID is answered `rate_limited`.

- Input: 30 per second: one per tick, plus room for a burst after a stall (backend step 18).
- Attack and PickUp: 10 per second. Attack cooldowns are also enforced in the simulation.
- ChatSend: 1 per second, burst of 3 (E1), enforced by the chat service per character rather than by the gateway's buckets, so a refused line is answered with a Response (`ok: false`, `chat_rate_limited`, no request ID) instead of being dropped silently.
- Party commands: 2 per second.
- Inventory and market commands: 5 per second.
- Login (REST): 5 per minute per username and per IP.

## Trust model (Stage 1, TD-24's default)

What a session token is, and what happens when it is stolen.

- **The token** is 32 random bytes, URL-safe base64, shown once at login (and once per Hello, rotated). The server stores only its SHA-256; a database leak yields no usable tokens. One active session per account: a new login revokes the older one.
- **Rotation:** every Hello answers with a new token in Welcome, and the client uses that one from then on. The token it sent keeps working once, within 60 seconds, so a retried Hello or a REST call already in flight still succeeds.
- **Reuse detection:** any other use of a retired token (a second use, or a use after the 60 seconds) is taken as theft: the session is revoked at once, every connection on it is closed with Kicked `session_expired`, and the current token stops working too. The legitimate player logs in again; the thief's copy is dead.
- **Lifetime:** a session ends after 7 days unused. Each valid use pushes that expiry, at most once every 10 minutes, and never past 30 days from login.
- **Checks while connected:** the account service tells every gateway at once when a session ends by reuse or logout, or an account's sessions end (`WatchSessions`, step 24), and the gateway closes those connections; it also re-checks every connection's session once a minute and closes the ones that ended (expired, logged out, reused) with Kicked `session_expired`, which catches what a broken stream missed. A second Hello on a session that already has a connection closes the older connection (`logged_in_elsewhere`).
- **Log out everywhere:** `DELETE /api/sessions` revokes every session of the account and closes its connections.
- **Login:** throttled at 5 per minute per username and per IP; an unknown username is verified against a dummy argon2id hash, so a wrong username takes as long as a wrong password and reveals nothing by timing.
- **Not in Stage 1:** binding a session to an IP or device, refresh tokens, and any client-side storage rule beyond "keep the token in memory and never in a URL"; TLS is the deployment's job, in front of the game server.

## Versioning

Hello carries a protocol version number. On a mismatch the server sends Kicked with the outdated-protocol reason, and the client reloads.
